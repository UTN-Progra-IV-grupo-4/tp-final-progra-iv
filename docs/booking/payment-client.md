# Booking payment processing

This guide describes the Booking flow for [issue #19](https://github.com/UTN-Progra-IV-grupo-4/tp-final-progra-iv/issues/19). Business processes payment through an internal port, Data applies conditional reservation transitions, and the consumer can continue payment after creating or finding a compatible `Retained` reservation. The gRPC adapter uses the shared contract in `src/Contracts/Protos/payment.proto`. Both the broker and payment continuation are disabled by default.

## Flow

For a retained reservation, Booking will call Payment through the shared gRPC contract, using `Reservation.Id` as the payment idempotency key. Booking owns the reservation state; Payment owns the charge and its idempotent result.

| Payment result | Booking state |
| --- | --- |
| Approved, while the reservation remains `Retained` and `ExpiresAt` is in the future | `Confirmed` |
| Declined | `Rejected`, reason `PaymentFailed` |
| Payment unavailable after bounded retries | `Rejected`, reason `PaymentUnavailable`, while the reservation is still eligible for a conditional transition |

The result must be persisted before Booking completes the broker message. A compatible redelivery should continue a reservation that is still `Retained` and unexpired; a terminal or expired reservation should not start another charge. State changes must be conditional on both status and expiration so a late response cannot confirm a reservation whose seat has been released. The team communicated acceptance of recording a late or otherwise unpaired charge in audit logs (#24), without an automatic refund; the decision still needs to be recorded in #19, and cross-service verification remains pending.

## Contract and configuration

The shared contract in `src/Contracts/Protos/payment.proto` (merged with #22; see `docs/contracts/payment.md`) defines `PaymentService.Charge` with `reservation_id` (`string`), `amount_cents` (`int64`), and `currency` (`string`). Its response has approved, declined, and unspecified statuses. Booking uses the generated client from `Contracts` and does not define a parallel `.proto`.

Issues #19 and #22 define one fixed price per seat in integer cents: Booking configures `Payment:AmountCents` and sends it as `amount_cents` without conversion. The default placeholder is zero, so a valid price must be configured before enabling payment processing. `Payment:Currency` is a three-uppercase-letter ISO 4217 string; Payment currently accepts `ARS` through a configurable `SupportedCurrencies` list. A repeated `reservation_id` with different amount or currency produces `INVALID_ARGUMENT`. Booking forwards `CorrelationId` as gRPC metadata `x-correlation-id`; service-token authentication (#11) still needs integration. Keep credentials and environment-specific addresses outside the repository.

No numeric price has been agreed. The `150000` cents in issues #19/#22 is an example, not the configured project price. Booking owns the value in `src/Booking/Booking.Api/appsettings.json` under `Payment:AmountCents` and `Payment:Currency`; the current `0` is invalid for an enabled payment flow. For local Development checks, override those keys with Booking.Api User Secrets or `Payment__AmountCents` and `Payment__Currency` environment variables while keeping both feature switches off until the integration is ready. Once the team agrees on a demo price, record the value in #19 and decide whether to version it in Booking's appsettings for reproducibility. Payment receives and stores the amount; Availability does not supply it.

Issue #19 provisionally proposes a configurable five-second gRPC deadline. `Payment:Deadline` defaults to five seconds and the adapter applies it to each `Charge` call. `Payment:Address` must be an absolute HTTP or HTTPS URL when payment is enabled; set it through local configuration, User Secrets or `Payment__Address`. The Business processor defaults to three calls with a one-second delay and checks reservation eligibility before each call. When payment is enabled, startup validation requires a positive amount, uppercase three-letter currency, positive deadline and attempt count, nonnegative delay, a valid address, and a worst-case call budget (`MaxAttempts × Deadline + (MaxAttempts − 1) × RetryDelay`) below half the configured retention duration. This leaves time for persistence and broker settlement. A local currency syntax check cannot replace Payment's supported-currency validation. The default 5-second deadline and retry values are Booking configuration choices, not course requirements.

## Verification and open decisions

Business logic and consumer settlement are tested with a fake Payment client. PostgreSQL integration tests cover conditional confirmation, expiration and competing payment transitions; duplicate delivery and persistence failure are covered locally with the fake. The adapter has tests against a local gRPC server for fields, statuses, errors, metadata and deadline. The demo in #25 also needs the approved path and Payment absent → `PaymentUnavailable`.

`BookingPaymentRealIntegrationTests` also runs Booking's message processor against Payment's actual gRPC service, Business and Data, using TestServer for the HTTP transport and separate PostgreSQL 16 Testcontainers databases. It never starts the Azure Service Bus consumer. The tests check matching Booking/Payment rows for `Approve` and `Decline`, `Error` producing `Unavailable` and `Rejected/PaymentUnavailable`, `Slow` producing `DeadlineExceeded` then `Pending`/DLQ while the single charge later becomes `Approved`, and repeated `reservation_id` returning the stored `ChargeId`. They assert the propagated `CorrelationId` and that captured Booking and Payment logs exclude the message's user payload. Run `dotnet test tests/Booking/Booking.Tests/Booking.Tests.csproj --filter 'FullyQualifiedName~BookingPaymentRealIntegrationTests' -m:1 -p:BuildInParallel=false -v minimal` with Docker available. A separately running Payment process is tested below; service authentication and a coordinated broker test remain open before the full deployment flow is verified.

`SeparatePaymentProcess_ReceivesBookingChargeOverLocalHttp2` extends that local check across an actual loopback HTTP/2 socket. The test starts `Payment.Grpc` in its own process with the project's `appsettings.json`, supplies an ephemeral PostgreSQL connection string and a temporary port through process environment variables, then invokes Booking's message processor as a local driver. It checks `Confirmed` and `Approved` in the two databases, amount and currency, `CorrelationId` in Booking and Payment logs, and absence of the user payload. The process and Testcontainers databases are disposed at the end. Run it with `dotnet test tests/Booking/Booking.Tests/Booking.Tests.csproj --filter 'FullyQualifiedName~SeparatePaymentProcess_ReceivesBookingChargeOverLocalHttp2' -m:1 -p:BuildInParallel=false -v minimal`. This does not start Booking.Api as a web process: with the broker off, Booking exposes no payment-triggering HTTP endpoint. Service authentication (#11) and the controlled broker flow remain separate validations.

Issue #22 specifies Payment's `SimulatedGateway:Mode` to select simulated outcomes independently of the fixed price. `Approve`, `Decline`, `Slow`, and `Error` are available; `Expire` is optional and not part of the agreed demo. Expiration is tested using `TimeProvider` with the official ten-minute retention.

The current Booking policy for ambiguous cases is: `Pending` maps to `ABORTED` and retries three times with the same `reservation_id`; exhausted attempts send the message to dead-letter while the reservation remains `Retained`. Final team acceptance of this three-attempt policy remains open in #19. The expiration job in #20 is integrated and releases the seat after the ten-minute retention. `Unavailable` and `DeadlineExceeded` use bounded retries with the same key; after exhaustion Booking persists `Rejected/PaymentUnavailable` and completes the message if the reservation is still eligible. If it expired during the attempts, Booking keeps it `Expired` and still logs the unknown payment result after completing the message. The #22 owner can reconcile it by looking up the Payment row by `reservation_id`; the shared contract has no lookup RPC. An observed late `APPROVED` does not confirm an expired reservation and has no automatic refund. It is logged as a late charge for the #24 owner to review. The no-refund limitation still needs explicit acceptance recorded in #19. Invalid Payment requests and unexpected responses use safe local dead-letter reasons pending team review. The #18/#19 owner follows the [Booking DLQ review procedure](payment-dlq-review.md). Payment retries do not depend on the subscription's uncontrolled `MaxDeliveryCount`.

Availability #15 generates `correlationId` in the message body. Booking accepts only ASCII letters, digits, `-`, `_` and `.` with a maximum of 128 characters; invalid values receive `CorrelationIdInvalid` in dead-letter. Booking passes the valid value to its payment port and the gRPC adapter sends it as `x-correlation-id` metadata. Payment currently logs only values of up to 64 characters, so end-to-end correlation for longer values needs an agreed limit. Audit records should include service name and result/error code alongside safe identifiers, without message body or credentials. The local logs cover selected outcomes; the complete cross-service audit belongs to #24.

## Startup checks and message lock

With `Payment:Enabled=true`, Booking registers the gRPC adapter and validates the payment options and address at startup (`ValidateOnStart`), instead of redelivering messages because of invalid configuration. Payment and the Azure Service Bus consumer remain disabled by default while service authentication (#11) and the coordinated broker flow are pending.

The worst-case payment time per delivery with the defaults is about 17 s (3 × 5 s deadline + 2 × 1 s delay), plus persistence. The consumer uses the Azure Service Bus SDK processor with its default automatic lock renewal (`MaxAutoLockRenewalDuration`, 5 minutes), so the subscription lock duration does not need to cover the whole bound; it only needs to be long enough for the SDK to renew it. Startup validation keeps the worst case under half the retention duration (5 minutes), which stays below that renewal limit. If the consumer is later configured with a shorter `MaxAutoLockRenewalDuration`, keep it above the payment time bound.
